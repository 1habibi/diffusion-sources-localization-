# Журнал разработки проекта

Этот файл кратко фиксирует ход разработки системы идентификации нескольких источников информационной диффузии. Его следует дополнять после завершения каждого существенного этапа. Материал предназначен для последующей подготовки проектной и практической глав ВКР.

## 1. Постановка задачи

В качестве основной выбрана многоисточниковая постановка. По известному графу социальной сети и неполному снимку распространения требуется:

- построить независимые оценки принадлежности каждого узла к множеству источников;
- определить неизвестное количество источников `k` от 1 до 3;
- сформировать итоговое множество найденных источников;
- оценить устойчивость решения к шуму, неполным наблюдениям и смене топологии.

Одноисточниковый режим сохранен как частный случай. Текстовая классификация публикаций как слухов или фейков в текущую задачу не входит: система локализует источники уже обнаруженного процесса распространения.

## 2. Архитектурное решение

Основной моделью стала `Joint Source-Count GCN` с общим двухслойным GCN-backbone и двумя выходными головами:

- узловая multi-label голова выдает один logit для каждого узла;
- count-голова классифицирует количество источников по классам 1, 2 и 3.

Функция потерь состоит из трех частей:

```text
L = L_source + lambda_count * L_count + lambda_cons * L_cons
```

В качестве обязательного нейросетевого baseline реализована `Node-only GCN` без count-головы. Для estimated-k режима у нее применяется порог, выбираемый только по validation.

## 3. Симуляция и наблюдения

Реализован многоисточниковый симулятор Independent Cascade. Все источники активируются одновременно на нулевом такте. Для каждого каскада сохраняются источники, времена заражения, история новых заражений и итоговая зараженная область.

Также реализован SI-симулятор для стресс-теста смены процесса распространения. В отличие от IC, зараженные узлы повторяют попытки передачи на последующих тактах.

Модуль наблюдений поддерживает:

- 100%, 75% и 50% наблюдаемых зараженных узлов;
- ложноположительные наблюдения;
- гарантированное сохранение источников в основном режиме;
- отдельный режим со скрытым источником и поиском по всем узлам графа.

Случайность симуляции и наблюдения разделена на `simulation_seed` и `observation_seed`.

## 4. Данные и графы

Для отладки используется Zachary Karate Club. На нем был проверен полный путь от симуляции до Streamlit-демо.

В качестве основной реальной топологии выбран SNAP ego-Facebook:

- 4 039 узлов;
- 88 234 неориентированных ребра;
- одна связная компонента;
- средняя степень около 43,69.

Facebook предоставляет только структуру связей. Источники и каскады генерируются программно, поэтому итоговые данные являются полусинтетическими.

Для внешнего теста загружен SNAP email-Eu-core. Он используется для проверки переноса зафиксированной модели на граф другого размера и структуры без дообучения.

Дополнительно реализованы генераторы Erdős-Rényi и Barabási-Albert для контролируемых экспериментов с топологией.

## 5. Формат датасета

Топология каждого графа хранится один раз в `graph.npz`. Split хранятся отдельно в `train.npz`, `validation.npz` и `test.npz`.

Для каждого примера сохраняются:

- узловые признаки;
- маска кандидатов;
- бинарный вектор источников;
- полная маска заражения;
- количество источников;
- скрытые источники;
- вероятность передачи;
- доля наблюдаемости;
- seed симуляции и наблюдения.

Основные признаки узла: статус наблюдаемого заражения и нормированная логарифмическая степень. Идентификаторы пользователей не используются, чтобы модель не запоминала конкретные вершины.

## 6. Baseline-методы и метрики

Реализованы классические методы:

- `Uniform candidates`;
- `Degree candidates`;
- `Multi-Jordan`.

Поддерживаются режимы `oracle-k` и `estimated-k`.

Основные метрики:

- precision, recall и F1 по множеству источников;
- exact set accuracy;
- count accuracy и count MAE;
- PR-AUC узловых оценок;
- направленные и симметричная средняя графовая ошибка локализации.

Метрики рассчитываются отдельно для `k=1`, `k=2`, `k=3` и агрегируются macro-способом.

## 7. Обучение и воспроизводимость

Реализованы циклы обучения Joint и Node-only GCN, early stopping и сохранение лучшего checkpoint. После каждой эпохи сохраняются общий loss, его компоненты, macro-F1, PR-AUC, count accuracy, count MAE, learning rate и длительность эпохи.

Результаты каждого запуска включают:

- копию YAML-конфигурации;
- `best_model.pt`;
- `history.csv` и `history.json`;
- `metrics.json`;
- test-предсказания по отдельным каскадам.

Добавлена поддержка mini-batch обучения и вычисления train/validation метрик. Все параметры и random seed задаются конфигурациями.

## 8. Тестирование

На ego-Facebook создан пилот из 498 каскадов:

- train: 300;
- validation: 99;
- test: 99.

Профилирование GCN на полном Facebook-графе показало, что batch size 3 быстрее обработки по одному графу и работает стабильно на CPU. Для основного обучения на 10 000 каскадах рекомендован GPU.

Подробности сохранены в `docs/facebook_pilot_report.md`.

## 15. Исправление загрузки данных в Colab

При первом запуске Joint-модели в Colab возникла ошибка `CUDA out of memory`: CLI переносил на GPU все примеры train/validation/test до начала обучения. Исправлен перенос данных: датасет остается в CPU RAM, а на GPU отправляется только текущий mini-batch внутри train, validation и test-циклов. Это сохраняет семантику обучения и делает реальное потребление VRAM зависимым от `batch_size`, а не от размера всего split. Аналогичная правка внесена для Node-only, включая подбор validation-порога. Профильные тесты обучения и CLI прошли: 13 тестов, `compileall` без ошибок.

Для наблюдения за длинными Colab-запусками в оба training-цикла добавлен вывод после каждой эпохи: train/validation loss, validation и best macro-F1, счетчик early stopping и суммарная длительность train/validation-оценки. Данные сохраняются в `last_checkpoint.pt` после вывода каждой строки.

Дополнительно подключены `tqdm`-индикаторы по mini-batch для обучения, train-оценки и validation в каждой эпохе. В Colab они показывают число обработанных batch, скорость и ETA; в программных вызовах без описания индикатор не выводится.

После переноса checkpoint между CPU и CUDA обнаружена ошибка восстановления `cuda_random_states`: `torch.load(..., map_location="cuda")` переносил RNG state на GPU, хотя `torch.cuda.set_rng_state_all` требует CPU `ByteTensor`. Загрузчик теперь явно возвращает все CUDA RNG state на CPU перед восстановлением. Добавлен регрессионный тест; профильная группа содержит 13 успешно прошедших тестов.

Colab notebook дополнен полным операционным сценарием: безопасное обновление репозитория без обязательного `rm -rf`, проверка файлов Facebook-датасета, проверка метрик и артефактов, генерация runtime-конфигураций и девять отдельных ячеек обучения для Joint full, Joint без consistency-loss и Node-only с seed 7026-7028. Каждый длительный запуск изолирован, чтобы результат можно было проверить перед следующим.

После первых трех запусков notebook переработан в линейную русскоязычную инструкцию с контрольными точками. Добавлены отдельный tuning-запуск `lambda_consistency=0,01`, сравнение коэффициентов только по validation, явный выбор лучшего коэффициента и условный порядок финальных повторов. Для случая, когда побеждает `lambda_consistency=0`, notebook требует пропустить дублирующие Best Joint ячейки и использовать no-consistency серию как финальную.

## 16. Первые результаты основного Facebook-обучения

На Tesla T4 завершены первые контрольные запуски с seed 7026. Joint full получил estimated-k F1 `0,3525`, count accuracy `0,6101` и count MAE `0,4880`. Node-only с validation-порогом `0,6` получил F1 `0,3670`, count accuracy `0,4354` и count MAE `0,7688`; лучшая эпоха 9, early stopping на эпохе 19, время обучения около 0,71 часа, peak VRAM около 11,08 GiB.

Node-only пока превосходит Joint full по estimated-k F1 примерно на `0,0146`, но заметно уступает по оценке количества источников. В oracle-k режиме узловое качество практически совпадает: F1 `0,3593` для обеих моделей. Это предварительный результат только для одного seed: статистический вывод будет сделан после проверки Joint без consistency-loss и повторов с seed 7027-7028.

Joint без consistency-loss с seed 7026 получил estimated-k F1 `0,3522`, count accuracy `0,6306`, count MAE `0,4309` и exact set accuracy `0,0666`. По F1 он практически совпал с Joint full (`0,3525`), но немного улучшил оценку количества относительно полной модели (`0,6101`). При текущем `lambda_consistency=0,1` положительный вклад consistency-loss не обнаружен; вывод требует повторов по seed.

Validation-only tuning для `lambda_consistency` на seed 7026 завершен. Получены значения: `0,1` -> F1 `0,355239`, count accuracy `0,622623`; `0,01` -> F1 `0,356373`, count accuracy `0,567067`; `0,0` -> F1 `0,355889`, count accuracy `0,628128`. Прирост F1 у `0,01` относительно `0,0` составляет всего `0,000484`, при этом оценка количества заметно хуже. Поэтому для финальной серии зафиксирован `lambda_consistency=0,0`; consistency-loss приводится как отрицательная абляция.

Финальные повторы seed 7026-7028 завершены для Joint без consistency-loss и Node-only. Средний estimated-k F1 Joint составил `0,3467` при count accuracy `0,6266`, exact set accuracy `0,0657` и симметричной графовой ошибке `1,1583`. Для thresholded Node-only средний F1 составил `0,3695`, count accuracy `0,4211`, exact set accuracy `0,0295` и графовая ошибка `1,0775`. Таким образом, Node-only устойчиво лучше по частичному совпадению и средней близости, а Joint примерно в 2,2 раза чаще полностью восстанавливает множество и существенно точнее оценивает его размер. Отображаемая validation count accuracy `1,0` у Node-only является техническим значением oracle-k evaluation, а не способностью модели оценивать количество; notebook скорректирован, чтобы показывать для нее `N/A` и отдельный validation thresholded F1.

Классические oracle-k baseline рассчитаны на основном test split из 1 998 примеров. F1 составил `0,1071` для Degree, `0,1714` для Uniform и `0,2735` для Multi-Jordan. GCN-модели с oracle-k F1 около `0,36` превосходят все три baseline по точному совпадению источников. Multi-Jordan при этом имеет меньшую среднюю графовую ошибку (`0,8537` против примерно `1,13-1,16` у GCN), поэтому итоговый анализ должен отдельно обсуждать точность идентификации и близость локализации.

Robustness для Joint без consistency с seed 7026 завершен на сетке 3 уровня наблюдаемости и 3 уровней ложноположительного шума. При отсутствии шума F1 составил `0,3188`, `0,3483` и `0,4091` для наблюдаемости 100%, 75% и 50%; при 10% шума значения снизились до `0,2158`, `0,2629` и `0,3372`. Count accuracy при 10% шума составила `0,3769`, `0,4054` и `0,4469`. Улучшение при снижении наблюдаемости объясняется сохранением источников и уменьшением candidate set; это ограничение основного протокола будет явно описано.

Process shift IC -> SI завершен на том же checkpoint: F1 изменился с `0,3522` на IC до `0,3463` на SI, count accuracy с `0,6306` до `0,6321`, а графовая ошибка с `1,1299` до `1,1000`. Смена процесса не вызвала существенного падения качества.

Transfer Facebook -> email-Eu-core без дообучения завершен на 90 каскадах. F1 снизился с `0,3522` внутри Facebook до `0,1744`, count accuracy до `0,3444`, count MAE вырос до `0,9556`, а графовая ошибка до `1,7704`. Это подтверждает ограниченный перенос на другую топологию и необходимость отдельного анализа domain shift.

Для продолжения без перезаписи результатов введен реестр версий в `docs/experiment_registry.md` и `configs/model_versions.yaml`. Текущая модель и все Colab-результаты считаются неизменяемой `v1_baseline`. Улучшения будут оформляться как `v2_improved` в отдельных каталогах `reports/diagnostics/facebook_main_v2`, `reports/series/facebook_main_v2` и `reports/runs/facebook_main_v2`; старые конфигурации и checkpoint не переиспользуются для записи.

## 17. Диагностика v1 и проверка приложения

Для `v1` добавлен отдельный `scripts/diagnose_v1.py`. Он не обучает модель и формирует в `reports/diagnostics/facebook_main_v1`:

- confusion matrix оценки `k` для Joint и Node-only;
- bootstrap CI по 1 998 тестовым каскадам;
- качество по диапазонам размера candidate set;
- PNG-графики и JSON/CSV-таблицы.

Диагностика показала, что Joint чаще всего путает `k=2` с `k=3`, а Node-only в thresholded-режиме часто завышает количество источников. Качество Joint снижается с ростом candidate set: F1 `0,4214` при 5-10 кандидатах, `0,3511` при 11-20, `0,2526` при 21-50 и `0,2171` при более 50 кандидатах. Это подтверждает, что следующая версия должна улучшать представление границы и глобального контекста каскада.

Streamlit получил переменные окружения `DIFFUSION_DATA_DIR` и `DIFFUSION_RUN_DIR`; default pilot-пути сохранены. Facebook v1 checkpoint проверен smoke-тестом и реальным inference через `streamlit.testing`: приложение стартует без исключений, inference отрабатывает, демо-метрики отображаются.

При проверке Facebook v1 обнаружено, что визуализация пыталась строить `spring_layout` на полном графе из 4 039 узлов, из-за чего веб-интерфейс долго оставался пустым. Визуальный слой переведен на локальную окрестность каскада максимум из 300 узлов; inference по-прежнему выполняется на полном графе, поэтому метрики и prediction не изменяются. Отдельно обработан случай, когда предсказанный узел находится за пределами отображаемой окрестности.

## 18. Зафиксированный протокол разработки v2

План улучшения модели переработан в последовательный экспериментальный протокол. Принято разделить следующую работу на две версии:

- `snapshot-v2` сохраняет один неполный снимок и исходные Facebook train/validation/test, поэтому напрямую сравнивается с `v1`;
- `temporal-v2` использует 2-3 последовательных снимка и является отдельной постановкой с собственными splits и holdout.

Для `snapshot-v2` зафиксирована лестница изолированных абляций. Относительно текущего победителя по validation по одному проверяются группы structural/distance-признаков, global-context голова, третий residual GCN-слой, специализированные головы для `k=1/2/3`, ranking-loss с hard negatives, нормированный Jordan-признак и safe shortlist. Отклоненный компонент не переносится дальше. После последовательного отбора обязательны leave-one-component-out проверки финального кандидата. Это устраняет прежнее рассогласование плана, где несколько изменений предлагалось добавить одновременно.

Приняты следующие архитектурные решения:

- global-context source-head объединяет embedding кандидата, mean/max pooling наблюдаемых узлов и кандидатов и глобальные характеристики каскада;
- specialized source-head обучаются по истинному `k`, а на inference выбираются предсказанным `k`; для разделения ошибок обязательны `estimated-k` и `oracle-k` режимы;
- ranking-loss формирует пары только внутри одного каскада и использует sampled/hard отрицательных кандидатов;
- Jordan centrality сначала проверяется как входной признак; post-hoc смешивание scores остается отдельной вторичной абляцией;
- shortlist допускается только при candidate recall не ниже `0,95` в целом и для каждого `k`, с bootstrap-контролем и fallback на полный candidate set;
- третий GCN-слой рассматривается как проверяемая гипотеза, а не как автоматическое следствие трех шагов симуляции.

В обязательный набор оценки добавлены `Hit@1-hop` и `Hit@2-hop`: для каждого истинного источника измеряется минимальное расстояние до предсказанного множества, после чего доля попаданий в радиус macro-усредняется по каскадам. Метрики публикуются вместе с F1, exact set accuracy, count accuracy/MAE, graph distance и разрезами по `k` и размеру candidate set.

Поскольку существующий test уже анализировался при диагностике `v1`, до реализации `snapshot-v2` решено создать закрытый `snapshot_final_holdout` с непересекающимися seeds и зафиксированными manifest/checksums. Он не используется для нормализации, tuning, early stopping или выбора checkpoint и открывается один раз после freeze конфигурации и checkpoints. Минимальный критерий заметного успеха: прирост holdout macro F1 не менее `0,03` относительно `v1 Joint`, положительный paired bootstrap CI, прирост F1 для `k=1` не менее `0,05` и отсутствие деградации более `0,02` по count accuracy и F1 для `k=2/3`.

Для отрицательного результата утвержден contingency-план: сначала аудит leakage, масок, scaling, candidate recall и воспроизводимости `v1`; затем разделение ошибок count/localization, learning curves и анализ по `k`; после этого выбор простейшего подтвержденного промежуточного варианта либо сохранение `v1`. Увеличение датасета допускается только при незавершившейся learning curve, а temporal-режим не должен маскировать отсутствие улучшения snapshot-постановки. После открытия final holdout перенастройка запрещена; новому циклу гипотез потребуется новый holdout.

На этом этапе изменена только документация. Реализация архитектуры, генерация holdout, конфигурации и обучение `v2` еще не начинались.

## 19. Начало инфраструктурного этапа snapshot-v2

Начато выполнение плана без изменения архитектуры основной модели. В общий evaluation pipeline добавлены `Hit@1-hop` и `Hit@2-hop`; метрика считает долю истинных источников, находящихся в заданном радиусе от предсказанного множества. Новые training/evaluation запуски сохраняют hop-метрики в per-example CSV и агрегатах. Для старых checkpoints `v1` создан отдельный сценарий повторной оценки, поскольку старые CSV не содержат идентификаторы предсказанных узлов и метрики нельзя восстановить из средней graph distance. Старые CSV и checkpoints не перезаписываются.

Переоценка шести frozen checkpoints завершена. Joint без consistency в estimated-k режиме получил `Hit@1-hop=0,5075` и `Hit@2-hop=0,9440`; для `k=1` `Hit@1-hop=0,3799`. Node-only thresholded получил соответственно `0,5903`, `0,9317` и `0,5646` для `k=1`. Высокий `Hit@2-hop` при умеренном `Hit@1-hop` показывает, что `v1` обычно находит правильную область, но недостаточно точно ранжирует узлы внутри нее.

До архитектурных изменений создан `snapshot_final_holdout` на исходном Facebook snapshot-протоколе: 1 998 примеров, dataset seed `3007026`. Проверено отсутствие пересечений simulation/observation seeds с train/validation/test `v1`. Набор запечатан со статусом `sealed_unopened`; target-зависимые агрегаты не вычислялись. SHA-256 данных, графа, конфигурации и seed-массивов сохранены в `configs/holdouts/facebook_snapshot_final_holdout_manifest.json`.

Training CLI получил обратносуместимый флаг `evaluation.evaluate_test`. Старые конфигурации `v1` без этого поля продолжают выполнять прежнюю test-оценку; новые абляции `snapshot-v2` используют `evaluate_test: false`, загружают только train/validation и не создают `test_predictions.csv`. Это технически закрепляет запрет выбора решений по test.

Добавлены конфигурации `S0` и `S1a`. `S0` полностью повторяет Joint `v1` без consistency-loss, но пишет в новый каталог. Для `S1a` реализован именованный builder признаков, который по доступному observed mask вычисляет нормированные число/долю наблюдаемых и ненаблюдаемых соседей и долю наблюдаемых узлов в замкнутой окрестности. Исходные двухколоночные архивы `v1` не изменяются. Локальный CPU smoke-run `S1a` на 18/9 примерах успешно завершен, использовал семь признаков и не загружал test.

Существующие Facebook training-конфигурации, Colab-notebook и инструкции явно помечены как `v1_baseline`; они сохранены. Новый полный notebook `snapshot-v2` будет создан рядом после готовности локального pipeline последовательных абляций. Полное обучение `S0/S1a` еще не запускалось.

## 20. Реализация distance/position-признаков S1b

Для `S1b` добавлена отдельная именованная группа признаков положения узла относительно наблюдаемого каскада. Реализованы среднее и максимальное расстояние до наблюдаемых узлов, расстояние до границы наблюдаемой области, индикатор отсутствия границы и эксцентриситет внутри связной компоненты индуцированного наблюдаемого подграфа. Расстояния capped значением `10` и нормированы в диапазон `[0,1]`; недостижимые пары получают capped-значение.

Чтобы не выполнять тысячи Python BFS перед каждым запуском, матрица кратчайших расстояний топологии рассчитывается блоками через SciPy, хранится как `uint16` и кэшируется в `data/cache/ego_facebook_shortest_paths.npz`. Кэш занимает около 1,3 МБ и загружается только после совпадения SHA-256 fingerprint отсортированного списка ребер и размера матрицы. Один builder переиспользуется для train/validation.

Добавлена feature-only диагностика, которая читает только observed masks и candidate masks train/validation; source labels, test и final holdout не загружаются. На 9 990 train и 1 998 validation примерах выявлено, что `distance_to_observation_boundary` почти вырожден: доля примеров с вариацией среди кандидатов `0,0216` на train и `0,0195` на validation, стандартное отклонение около `0,003`. `observation_boundary_missing` всегда равен нулю. Эти два признака исключены из GPU-конфигурации до обучения.

Оставленные признаки имеют стабильную вариативность: mean distance меняется примерно в `99,5%` примеров, max distance — примерно в `45%`, induced eccentricity — примерно в `96,5%`; train/validation статистики близки. Итоговая `S1b` содержит 10 признаков: семь из `S1a` и три distance/position-признака. Локальный CPU smoke-run на 18/9 примерах завершен успешно, использовал только train/validation и не создал test predictions. Полученный на таком размере F1 не интерпретируется как результат абляции.

## 21. Реализация глобальных скаляров S1c

Для `S1c` реализованы graph-level признаки, повторяемые для всех узлов конкретного каскада при неизменной архитектуре `v1`: нормированный размер observed set, нормированный размер candidate set, отношение observed/candidates, плотность индуцированного наблюдаемого подграфа, нормированное число его связных компонент и доля узлов в крупнейшей компоненте. Все величины рассчитываются только из графа, observed mask и candidate mask.

Feature-only диагностика выполнена на полных train/validation без source labels, test и holdout. Она выявила две особенности основного протокола: `candidate_count_normalized` точно совпадает с `observed_count_normalized`, а `observed_candidate_fraction` всегда равен `1,0`. Оба признака исключены до GPU-обучения. Оставленные четыре скаляра имеют близкую межпримерную вариативность на train/validation: observed size `example_mean_std≈0,097`, density `≈0,199`, component count `≈0,179`, largest-component fraction `≈0,180`.

Итоговая конфигурация `S1c` содержит 14 входных признаков: 10 из выбранной `S1b` и четыре глобальных скаляра. Локальный CPU smoke-run на 18/9 примерах завершился успешно, test не загружался и test predictions не создавались. Значение F1 этого smoke-run не используется для выбора абляции. Следующим архитектурным шагом является `S2` — передача global context непосредственно в source-head вместо надежды, что повторяемые скаляры полностью усвоятся через backbone.

## 22. Реализация global-context source-head S2

Для `S2` добавлен обратимо совместимый режим `source_head_mode: global_context`. Двухслойный GCN-backbone, count-head, признаки `S1c` и функция потерь не изменены. Для каждого узла-кандидата новая source-head объединяет его hidden embedding, mean/max pooling hidden embeddings по observed set, mean/max pooling по candidate set и отдельный вектор из четырех выбранных graph-level скаляров. Полученный контекст обрабатывается двухслойной MLP с dropout и выдает один source logit на кандидата.

Режим `local` остается значением по умолчанию и сохраняет прежнюю линейную source-head и имена параметров, поэтому конфигурации и checkpoints `v1` не переводятся на новую архитектуру. Dataset теперь дополнительно передает `global_features` формы `[1, 4]`; при batch-загрузке они образуют `[batch_size, 4]`. Добавлены проверки наличия кандидатов, размерности global context и согласованности `global_feature_dim` с выбранными признаками.

Созданы полная и smoke-конфигурации `configs/snapshot_v2/s2_global_context.yaml` и `configs/snapshot_v2/s2_global_context_smoke.yaml`. CPU smoke-run на 18/9 примерах завершился успешно; test не загружался, `test_predictions.csv` не создан. В smoke-варианте число параметров выросло с `1 620` у локальной головы `S1c` до `2 980`; это ожидаемая цена контекстной MLP. Метрики столь малого запуска не интерпретируются и решение о принятии `S2` будет приниматься только после одинакового GPU-budget по validation.

## 23. Реализация residual GCN S3

Для `S3` добавлен режим backbone `residual_3`. Первый `GCNConv` переводит 14 входных признаков в hidden space. Выход второго слоя складывается с его hidden-входом до ReLU; после dropout третий слой аналогично складывается со входом. Таким образом, receptive field увеличивается до трех message-passing слоев, а skip-связи сохраняют более неглубокое представление и дают прямой путь градиенту.

Абляция меняет только backbone: набор признаков `S1c`, global-context source-head `S2`, count-head, dropout, loss и training budget сохранены. Старый режим `plain_2` остается значением по умолчанию; при нем `conv3` не создается, поэтому архитектура и state dict checkpoints `v1` не изменяются. Training summary теперь явно сохраняет `backbone_mode`.

Созданы `configs/snapshot_v2/s3_residual_gcn.yaml` и `configs/snapshot_v2/s3_residual_gcn_smoke.yaml`; в контрольные конфигурации `S2` добавлено явное `backbone_mode: plain_2`. Unit-тест проверяет форму выхода, наличие третьего слоя, совместную работу с global-context и ненулевой градиент параметров `conv3`. CPU smoke-run на 18/9 примерах завершился успешно, test не загружался и `test_predictions.csv` не появился. Число параметров smoke-модели выросло с `2 980` до `3 252`, то есть только на параметры третьего `GCNConv`. Метрики smoke-run не используются для решения `accepted/rejected`; оно принимается после одинакового полноразмерного GPU-запуска по validation.

## 24. Реализация специализированных source-head S4

Для `S4` общая source-head заменена тремя независимыми головами для `k=1`, `k=2` и `k=3`. Общими остаются 14 входных признаков, residual backbone `S3`, формирование global context `S2` и count-head. Модель возвращает source logits формы `[num_nodes, 3]`; каждый столбец является ранжированием кандидатов своей головы.

Во время обучения BCE маршрутизируется по истинному `source_count` отдельно для каждого графа batch, поэтому градиент source-loss получает только соответствующая этому графу голова. Это допустимый обучающий target, но он не используется как скрытая подсказка при обычной оценке: `estimated-k` сначала получает `k` из общей count-head и только затем выбирает соответствующий столбец source logits. `oracle-k` выбирает столбец по истинному `k` исключительно как явно обозначенная диагностика, отделяющая ошибки count estimation от localization. PR-AUC validation теперь также рассчитывается по scores головы, реально выбранной estimated-k маршрутом.

Режим `source_head_strategy: shared` остается значением по умолчанию и сохраняет архитектуру/state dict `v1-S3`; специализированный режим включается явно как `specialized_k`. Созданы `configs/snapshot_v2/s4_specialized_heads.yaml` и smoke-вариант. Тесты проверяют размер `[nodes, 3]`, выбор разных голов для predicted/oracle `k`, маршрутизацию разных графов batch и отсутствие градиента в невыбранных source-head logits.

CPU smoke-run на 18/9 примерах завершился успешно, test не загружался и test predictions не создавались. Число параметров smoke-модели выросло с `3 252` у `S3` до `6 006` у `S4`, поскольку вместо одной context MLP обучаются три. Метрики малого запуска не интерпретируются. Принятие `S4` потребует одинакового GPU-budget и обязательных validation-разрезов F1/Hit по `k=1/2/3`, особенно проверки отсутствия деградации `k=2/3`.

## 25. Реализация ranking-loss S5

Для `S5` в Joint objective добавлен член `lambda_rank * L_rank`, где `L_rank = softplus(score_negative - score_positive)`. Положительными считаются только истинные источники, отрицательными — только ложные узлы внутри `candidate_mask` того же графа. Batch index используется как жесткая граница: пары между каскадами не создаются. До ranking-loss logits специализированных голов `S4` маршрутизируются по истинному `k` каждого графа, как и для BCE.

Число отрицательных ограничено параметром `rank_negatives_per_positive`. Доля `rank_hard_negative_fraction` выбирается из ложных кандидатов с наибольшими текущими logits; остаток на train семплируется через PyTorch RNG. Resume-checkpoint уже сохраняет и восстанавливает это состояние. При вычислении train/validation metrics остаток выбирается детерминированно по диапазону ранжированных кандидатов, поэтому повторная оценка не вносит случайность в diagnostic ranking loss. Если `lambda_rank=0`, ranking-loss не рассчитывается вообще: контроль не получает лишних вычислений и не изменяет RNG относительно `S4`.

Созданы обязательный контроль `configs/snapshot_v2/s5_ranking_control.yaml` и включённый вариант `s5_ranking_loss.yaml`. Стартовые, ещё не принятые значения включённого варианта: `lambda_rank=0.2`, максимум 8 negatives на источник, hard fraction `0.5`. Они подлежат ограниченному сравнению только по validation; нулевой контроль обязателен. Smoke-конфигурация на 18/9 примерах завершила один CPU epoch, сохранила ненулевые train/validation ranking losses около `0.694`, не загрузила test и не создала test predictions. Число параметров осталось `6 006`, как у `S4`; малые smoke-метрики качества не интерпретируются.

## 26. Реализация Multi-Jordan-признака S6

Первоначально для `S6` был проверен непрерывный center-score, объединяющий максимальное и среднее расстояние кандидата до observed set. До GPU обнаружено, что он является точной линейной комбинацией уже включённых `max_distance_to_observed_normalized` и `mean_distance_to_observed_normalized`, то есть не добавляет информации. Этот вариант отклонён и заменён на set-aware признак, действительно воспроизводящий Multi-Jordan.

Итоговый `multi_jordan_rank_normalized` строит полный жадный порядок `candidate_mask`. На каждом шаге кандидат выбирается по тому же критерию, что `baselines.multi_jordan`: минимум максимального расстояния observed-узла до ближайшего выбранного центра, затем минимум суммы расстояний и node ID. Порядок нормируется от `1.0` для первого до `0.0` для последнего кандидата; узлы вне candidate set получают ноль и не участвуют в loss/inference. Признак использует только фиксированную топологию, observed mask, candidate mask и защищённый fingerprint distance-cache. Истинные источники и `source_count` не читаются.

Эквивалентность top-`k` существующему baseline проверена для `k=1/2/3` на path graph и 20 случайных observed/candidate подмножествах Karate graph. Полная feature-only диагностика прочитала только train/validation masks. Jordan rank менялся внутри candidate set во всех примерах; train/validation `std` составили `0.3020/0.3018`, диапазон — `[0,1]`, точных дубликатов с другими признаками нет. Среднее около `0.5` и почти нулевой `example_mean_std` следуют из нормирования полного ранга и не означают отсутствие внутриграфовой вариативности.

Созданы `configs/snapshot_v2/s6_jordan_feature.yaml` и smoke-вариант с 15 входными признаками. CPU smoke-run на 18/9 примерах завершился без test и test predictions. Число параметров выросло с `6 006` до `6 022` только из-за дополнительного входного веса первого GCN (`+64` параметра в полной hidden-64 модели). ## 27. Реализация safe shortlist S7

Для `S7` добавлена отдельная линейная preliminary-head, получающая тот же candidate/global context, что ranking-head. Её вход вызывается через `detach`, поэтому preliminary BCE обновляет только параметры preliminary-head: backbone, count-head и specialized ranking-head родительского варианта не получают дополнительный градиент. Голова создаётся после всех существующих модулей, а отключённый `shortlist_mode` не добавляет state dict ключей, сохраняя совместимость `v1-S6`.

Обычный `forward` выполняет полный scoring и служит внутренним контролем того же checkpoint. `forward_shortlisted` сначала оценивает всех допустимых кандидатов preliminary-head, строит top-`M` отдельно для каждого графа batch и запускает специализированные ranking-head только на выбранных строках source context. Остальные logits равны `-inf`. Если preliminary scores нечисловые, shortlist пуст или selection завершается контролируемой ошибкой, mask заменяется полным candidate set и фиксируется fallback flag. Значения `M` меньше трёх запрещены в validation-grid, чтобы shortlist мог вместить максимальное предсказываемое `k`.

Добавлен validation-only evaluator. Для каждого заранее указанного `M` он сравнивает один checkpoint в full и shortlist режимах, синхронизирует CUDA для end-to-end latency и сохраняет micro candidate recall, recall отдельно по `k=1/2/3`, 95% bootstrap CI, macro F1, candidate reduction и fallback rate. Вариант eligible только при micro/per-k recall не ниже `0.95`, нижней границе CI не ниже `0.93` и улучшении F1 или latency. При отсутствии eligible-вариантов сохраняются `selected_size: null` и `decision: reject_shortlist`; никакого автоматического отсечения в финальной модели не происходит.

Созданы `configs/snapshot_v2/s7_safe_shortlist.yaml` и smoke-вариант. Полная сетка зафиксирована как `M=[8,12,16,24,32]`, `bootstrap_repeats=2000`; preliminary loss имеет стартовый вес `1.0`. В smoke-модели preliminary-head добавила 85 параметров (`6 022 -> 6 107`; в полной hidden-64 модели будет `+325`). Один CPU epoch на 18/9 примерах прошел без test. Механизм корректно отклонил smoke-сетку: для `M=8` micro recall был `0.9444`, recall `k=3` — `0.8889`, нижняя граница CI — `0.8375`. Эти числа не характеризуют обученный S7, а лишь подтверждают, что F1/latency не обходят safety gates.

## 28. Полный Colab-сценарий snapshot-v2

После локальной готовности S0-S7 создан `notebooks/colab_training_snapshot_v2.ipynb` рядом с сохранённым `notebooks/colab_training.ipynb` версии `v1`. Новый notebook не использует `Run all`: каждая длительная абляция запускается отдельно, затем пользователь фиксирует `accepted/rejected` с комментарием. Состояние current winner, каталогов запусков и решений хранится в `reports/runs/facebook_main_v2/colab_ablation_state.json` на Drive, поэтому после разрыва runtime следующий конфиг строится от фактически принятого победителя. Отклонённые компоненты не переносятся автоматически.

Notebook включает GPU/runtime-проверку, установку без замены CUDA PyTorch, проверку только `graph/train/validation`, GPU smoke, S0-S4, ограниченную S5-сетку с нулевым parent-control, S6, автоматические safety gates S7, leave-one-component-out и отдельные frozen seeds 7027/7028. Перед финальными seed создаётся freeze manifest с SHA-256 конфигурации и полным журналом решений. Все runtime-конфигурации принудительно получают `evaluation.evaluate_test: false`; notebook явно останавливается до test/final holdout.

Для обоснованных Colab-решений training CLI теперь всегда сохраняет `validation_predictions.csv` и `validation_prediction_metrics` с estimated/oracle режимами, F1 по `k=1/2/3`, exact set accuracy, count metrics, graph distance и Hit@1/2-hop. Это не открывает test: при test-lock по-прежнему загружаются только train/validation, а `test_predictions.csv` отсутствует.
