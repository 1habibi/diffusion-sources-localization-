# Независимая проверка known-k Temporal-GCN на новых каскадах Facebook

Дата: 2026-10-05. Статус: письменный дизайн одобрен пользователем сообщением «го»; реализация требует отдельного плана, открытие набора — отдельного подтверждения после seal.

## Цель и границы

Проверить, сохраняется ли преимущество обучаемой Temporal-GCN над фиксированным Temporal-v3 на **новых каскадах той же Facebook-топологии**. Проверяются три заранее обученных checkpoint GCN: pilot 7026 и повторы 7027/7028. На прежней exploratory validation все три дали положительный ΔF1; эти результаты не заменяют независимую оценку. Новое обучение, подбор seed, beta, архитектуры или порогов здесь запрещены.

Сохраняются разные постановки задачи:

| Режим | Вход модели | Число источников |
| --- | --- | --- |
| Snapshot S1b, действующий режим приложения | Конечный снимок | Модель оценивает сама |
| Temporal-v3, действующий режим приложения | Ранний и конечный снимки | Модель оценивает сама |
| Known-k Temporal-v3 control и новая Temporal-GCN | Ранний и конечный снимки | Истинное `k` задано извне |

Главная независимая пара — **known-k GCN против known-k Temporal-v3** на одинаковых входах и одних каскадах. Существующую snapshot-only S1b seed 7026 дополнительно оцениваем с **её собственным estimated-k** и показываем в отдельной описательной таблице; это не равный по доступной информации участник главной пары. Можно сохранить также snapshot oracle-k как технический диагностический столбец из прежнего evaluator, но не смешивать его с operational estimated-k. Старые checkpoint, код старых режимов, Streamlit UI, `master` и `thesis_report/` не меняются. Перенос на другую топологию — отдельный будущий эксперимент.

## Выбранный подход и отвергнутые альтернативы

Создать один новый sealed holdout из 1 998 каскадов на той же исходной графовой структуре. Переиспользование уже открытого independent-набора Temporal-v3 не считается новым слепым подтверждением; старый snapshot holdout имеет иное заранее закреплённое назначение. Немедленная проверка на другом графе смешала бы новый метод с задачей переноса. Новый набор проверяет обобщение на другие каскады **условно на том же графе и синтетическом IC-протоколе**, но не на реальных эпидемиях или другой сети.

## Замороженные входы до генерации

- Проверить неизменённые `complete`/manifest/SHA старого known-k pilot (`freeze`, `smoke`, `pilot`), repeat stages (`freeze`, `seed_7027`, `seed_7028`, `summary`) и их identities. Старый summary должен иметь `status=completed`, фиксированные seeds и `positive_delta_each_repeat=true`.
- Зафиксировать точные SHA-256 трёх `best_model.pt`, конфигурацию модели/признаков, старый S1b seed 7026 `best_model.pt`/`config.yaml`, граф, raw graph и версии runtime. Один и тот же S1b/7026 служит основой фиксированного known-k Temporal-v3 control для всех трёх пар; он не переобучается. Ни один GCN checkpoint не выбирается по новому holdout; все три оцениваются независимо, без ансамбля.
- Зафиксировать неизменные раннее наблюдение после IC `t=1`, source-blind RNG/replay, те же пять финальных признаков, известное истинное `k ∈ {1,2,3}` для главной пары, candidate mask и Temporal-v3 `beta=0.5`. Число `k` является дополнительным входом только в known-k постановке; snapshot-only estimated-k его не получает.
- Проверить SHA исходников пакета против pilot 7026. Новый generator/evaluator/notebook располагается вне `src/diffusion_sources/*.py` (например, в `scripts/`), чтобы не нарушить уже замороженную code identity. Новые собственные исходники также входят в SHA freeze. Старые immutable артефакты только читаются.
- До freeze проверить наличие старых reference `train/validation/test`, прежнего независимого архива и metadata старого snapshot holdout на Drive. Отсутствующий файл — явный стоп и запрос точного пути, без создания замены. Для непересечения используются только seed metadata; labels/метрики старого snapshot holdout не читаются.

## Новый набор и изоляция случайных seed

Тот же `ego_facebook`/node mapping и параметры прежнего генератора: IC source counts `[1,2,3]`, probabilities `[0.01,0.02,0.03]`, `max_steps=3`, distance ranges `[{min:1,max:2},{min:3,max:5}]`, observation fractions `[1.0,0.75,0.5]`, `false_positive_count=0`, `hide_source_count=0`, `min_candidates=5`, `max_infected_fraction=0.5`, `max_attempt_factor=100`, `distance_cache_size=512`. Единственное изменение генерационного протокола — заранее назначенный **dataset seed `5007026`**. Один split `independent_holdout=1998`, с 666 каскадами для каждого истинного `k` по прежнему расписанию.

При старом правиле `simulation_seed=base+2*attempt`, `observation_seed=simulation_seed+1` все потенциальные seed лежат в `[5007026, 5406625]`. До генерации проверить отсутствие пересечений этого диапазона с объединением simulation/observation seeds старых train/validation/test, прежнего independent holdout и snapshot holdout. После генерации проверить фактическую уникальность и непересечение. Совпавшие исходы каскадов сами по себе не удалять; при пересечении seed — остановка, а не автоматический выбор нового base seed. Финальные features/candidate protocol и отсутствие утечки source labels в model input должны совпадать со старым генератором.

Новые отдельные пути на Drive: `data/generated/facebook_known_k_temporal_gcn_independent_v1` и `reports/runs/known_k_temporal_gcn_independent_evaluation/v1`. Старые данные и отчёты не перезаписываются. Частичный output не стирать и не регенерировать под тем же именем молча.

## Защищённый жизненный цикл

1. **Preflight/freeze:** до генерации аутентифицировать старые checkpoint, manifests, code/config/data identities, runtime и новый evaluation protocol. Зафиксировать SHA всего, что определяет результат; не читать новые target values.
2. **Generate/seal:** один раз создать 1 998 новых каскадов. Генератор технически сохраняет labels, но seal проверяет schema, размеры, graph fingerprint, hashes и seed metadata без вычисления target-метрик, распределения ошибок, early coverage или F1. Оставить `sealed_unopened`; напечатать manifest и STOP.
3. **Open:** только после отдельного точного подтверждения пользователя записать append-only `opened` marker, **до** первого доступа evaluator к новым labels. Открытие необратимо для статуса независимой проверки. При ошибке seal или смене identity не открывать.
4. **Evaluate:** на ровно тех же 1 998 индексах и одинаковых ранних масках получить frozen S1b logits/count для контроля и отдельного snapshot-only estimated-k; затем оценить GCN 7026, 7027, 7028. Для каждого seed сравнить GCN с known-k Temporal-v3 по тем же true sources, `k`, candidate sets и control predictions. Не переобучать и не выбирать лучшую GCN по результату. Сохранять полный per-cascade отчёт, checkpoint/input hashes и SHA-checked stage; Colab печатает только компактную сводку.
5. **Summary:** потребовать три завершённые проверенные seed-stage; сверить index order, truth, candidate/early-mask fingerprints и равенство контрольных прогнозов. Сформировать заранее определённые метрики/критерий. Повторный вызов готовой стадии только читает аутентифицированный результат. При обрыве разрешено продолжать одну и ту же оценку только с неизменными identities; нельзя регенерировать набор или менять суффикс ради нового шанса.

Новое evaluation notebook должно иметь явные ячейки setup → paths → read-only preflight → freeze → generate/seal → STOP → typed open → seed 7026 → seed 7027 → seed 7028 → summary. Никакого `Run all`, автоматического open или GPU fit. После каждого дорогостоящего/необратимого шага — короткий вывод и остановка для проверки пользователем.

## Метрики и заранее заданное решение

Первичная величина — разница `F1(GCN_known_k) − F1(Temporal-v3_known_k)` на каждом каскаде и каждом seed. Для общей точки сначала усреднить три seed-дельты **по одному и тому же cascade index**, затем усреднить по 1 998 индексам. Парный стратифицированный по истинному `k` bootstrap: 2 000 повторений, RNG seed `9282026`, 95% percentile CI. Не трактовать 3 × 1 998 предсказаний как 5 994 независимых случая. Показать индивидуальные F1/Δ/CI для каждого seed, среднее и sample SD трёх seed, но не выбирать лучший.

Подтверждение преимущества требует **всех** заранее согласованных условий: средняя ΔF1 ≥ `+0.02`, нижняя граница общего CI > 0, ΔF1 > 0 у каждого из трёх seed. Если любое условие не выполнено, сохранить полный отрицательный результат без новой настройки на этом holdout. Никакие вторичные показатели не отменяют этот первичный критерий.

Для known-k пары дополнительно публиковать precision/recall/F1, exact-set accuracy, symmetric set distance, Hit@1/2-hop и описательные разрезы по `k=1/2/3` и числу кандидатов `1–10/11–20/21–50/51+`. `count_accuracy` для known-k помечать N/A: true `k` подано на вход. Отдельная snapshot-only S1b estimated-k таблица показывает те же применимые метрики **и** count accuracy/MAE; прямой primary gate между неравными входами не строить. По одному короткому summary нельзя заявлять процент полного точного угадывания, пока не проверены `exact_set_accuracy` и полный manifest.

Вывод ограничен новыми синтетическими IC-каскадами на известной Facebook-топологии с прежними candidate/observation допущениями. CI условен на графе, протоколе и трёх frozen checkpoint. Результаты по подгруппам описательные, без post-hoc заявлений о значимости.

## Проверки до реального Colab

Локальные RED→GREEN тесты: отсутствие/подмена старых manifests/checkpoints/config/source hashes; выходной путь внутри защищённых входов; неверная graph topology; пересечение потенциальных и фактических seeds; преждевременное чтение labels/метрик до opened marker; повторная генерация или запись готовой стадии; обрыв при seal/open/inference; изменённые индексы/ранние маски/контроль/число кандидатов; честный bootstrap по каскадам, отрицательные gates, отдельная estimated-k таблица. После полного тестового прогона и review публиковать только новую экспериментальную ветку; `master`, старый UI и чистовой `thesis_report/` не менять.
