# Фиксированные повторы known-k Temporal-GCN после положительного pilot

Дата: 2026-10-03. Статус: проект дизайна для проверки пользователем. База: `experiment/known-k-temporal-gcn`, pilot seed 7026 с `quality_gate.passed=true`.

## Цель и границы

Проверить устойчивость уже зафиксированного выигрыша обучаемой known-k Temporal-GCN над Temporal-v3 при двух наблюдениях и заранее известном числе источников `k`. Обучить ровно два заранее названных seed — 7027 и 7028 — на прежнем train-архиве и оценить на той же validation-выборке. Результат остаётся **исследовательским**: старый validation уже использовался в разработке, а независимый набор этим этапом не открывается.

Никакого изменения архитектуры, пяти конечных признаков, раннего наблюдения, loss, `beta=0.5`, batch size, learning rate, patience, лимита эпох, порядка split или postprocessing. Никакой сетки гиперпараметров и выбора лучшего seed. Замороженные S1b, Temporal-v3, pilot 7026, старый unknown-k UI и `thesis_report/` не меняются.

## Почему нужен отдельный runner

Манифест pilot 7026 хэширует **все** `src/diffusion_sources/*.py`. Изменение существующего Python-пакета ради повторов сделало бы его защитную проверку несовместимой с уже завершённым run. Поэтому повторный контур помещается вне пакета, например `scripts/known_k_temporal_repeats.py`, с отдельным Colab notebook и output root. Он переиспользует неизменённые data builder, `NodeOnlyGCN`, trainer и парный evaluator пакета. Ветка повторов отделяется от опубликованной ветки pilot; ни один существующий исходник пакета не изменяется. Тесты обязаны обнаружить случайное изменение пакета до публикации.

Рассмотренные альтернативы: (1) переделать старый `run_stage` и заново заморозить/обучить 7026 — лишнее длительное обучение и путаница с уже открытым validation; (2) вставить обучение прямо в Colab-ячейки — меньше кода, но нет полноценной проверки identity, resume и результатов. Выбран отдельный runner с тестируемыми стадиями.

## Входы и неизменяемая идентичность

Перед любым новым fit стадия `freeze` проверяет прежний pilot: `complete`, манифест и SHA-256 каждого его артефакта, включая `best_model.pt` и `payload.json`; пересчитывает его input identity через **тот же** неизменённый Python-пакет и требует `quality_gate.passed is True`. Это также проверяет исходные data/config/frozen-S1b и хэши исходников, записанные в 7026. Если код пакета или входы отличаются, новый output не создаётся. Дополнительно фиксируются SHA-256 самого repeat-runner, нового notebook, пилотного манифеста и pilot checkpoint. После freeze изменение любого из этих файлов запрещает следующий этап в том же output root.

Конфигурация повторов содержит только список seed `[7027, 7028]`, ссылку на точный pilot-конфиг и критерий продолжения `delta_f1 > 0` для каждого seed. Её собственный SHA-256 входит в identity. Параметры тренировки читаются из уже проверенного pilot-конфига; менять их через notebook или CLI нельзя. Dataset seed и каскады не пересоздаются: меняется только seed инициализации/обучения модели.

## Стадии, данные и результаты

Новый Drive output root: `/content/drive/MyDrive/diffusion-sources/reports/runs/known_k_temporal_gcn_repeats/v1`. Только append-only стадии `freeze`, `seed_7027`, `seed_7028`, `summary`. Старый `/known_k_temporal_gcn_pilot/v1` читается, но не перезаписывается. Повторный вызов готовой стадии возвращает только проверенный результат; частичная стадия не перезаписывается молча. Явный resume допустим лишь с checkpoint, чей SHA-256, seed и frozen identity совпадают; если безопасное восстановление невозможно, работа останавливается с понятным сообщением.

Для каждого seed обучение идёт на тех же 9 990 train-каскадах, checkpoint выбирается по тем же 1 998 validation-каскадам. Сохранённая best-модель даёт парные прогнозы на тех же примерах и candidate masks; сравнение — frozen S1b snapshot и Temporal-v3 с известным `k`, `beta=0.5`. Сохраняются `best_model.pt`, `last_checkpoint.pt`, history, полные per-example metrics, агрегаты, SHA-256 manifest, время fit и число параметров. `count_accuracy` здесь N/A. Проверка равенства контрольных прогнозов/метрик с pilot 7026 защищает от незаметной смены сравнения.

Каждый новый seed запускается только после отдельного подтверждения в Colab. Сначала 7027 и STOP с коротким выводом. Если его `delta_f1 <= 0`, протокол признан не прошедшим устойчивость и 7028 **не запускается автоматически**, чтобы не тратить GPU на уже отрицательное решение; результат сохраняется. Если 7027 положителен, после согласования запускается 7028. `summary` показывает pilot 7026 и каждый завершённый repeat по отдельности, среднее только по фактически завершённым seed и sample SD при наличии минимум двух seed (иначе N/A), разрезы по `k`/candidate count и `positive_delta_each_repeat`. Не объединяет 1998 каскадов разных seed как независимые 5994 наблюдения и не объявляет новый CI независимой проверкой.

Критерий перехода к следующему **отдельному** дизайну: положительная `delta_f1` у 7027 и 7028 без изменения конфигурации; пилотный gate 7026 уже выполнен. При неуспехе любого повтора — честный отрицательный вывод, без подбора на validation и без открытия holdout. При успехе — только план нового, ранее не открытого independent holdout с отдельным seal/open; никакой автоматической оценки на нём. UI известного `k` и перенос checkpoint в локальное приложение тоже отдельные задачи после подтверждения.

## Colab и проверки

Новый notebook имеет явные ячейки: setup отдельной ветки и версии кода; пути; read-only preflight; freeze в **новом** output root; подтверждение 7027; run 7027 и STOP; проверка его `delta_f1`; подтверждение 7028; run 7028 и STOP; read-only summary. `Run all` не может молча начать два обучения. Вывод по умолчанию короткий — нельзя печатать 1998 per-example rows в Colab; полный отчёт остаётся на Drive. Инструкция указывает точную следующую ячейку и расшифровывает показатели без заявления об успехе до фактического результата.

Тесты до Colab: identity и защита старого pilot, запрет любого `test.npz`/holdout, фиксированные seed/гиперпараметры, несовпадение примеров/контроля, отказ при смене source/script/config/checkpoint, resume и аварийная финализация, отрицательный 7027, положительные два seed и корректный summary, явное подтверждение каждой GPU-ячейки. Локальный synthetic smoke проверяет механический путь; F1 на нём не интерпретируется. Ход и ограничения записываются в `development_log.md`; чистовой `thesis_report/` этим этапом не меняется.
