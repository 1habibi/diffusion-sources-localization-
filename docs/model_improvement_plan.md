# Состояние модели и план улучшений

Документ предназначен для переноса контекста в новый чат. Он фиксирует фактические результаты основной серии и варианты улучшения модели.

## 1. Что уже сделано

Реализована система локализации от одного до трех источников информационной диффузии на известном графе социальной сети.

Pipeline:

```text
Facebook-граф + неполный снимок каскада
        -> признаки узлов
        -> GCN
        -> scores источников + оценка k
        -> множество предполагаемых источников
```

Основной граф - SNAP ego-Facebook:

- 4 039 узлов;
- 88 234 неориентированных ребра;
- средняя степень около 43,69.

Основной датасет полусинтетический: топология реальная, а IC-каскады, источники и наблюдения сгенерированы программно.

Размеры датасета:

- train: 9 990;
- validation: 1 998;
- test: 1 998.

Распределение сбалансировано по `k=1,2,3`, вероятностям IC и долям наблюдаемости.

Основные условия:

- Independent Cascade;
- вероятности передачи `0.01`, `0.02`, `0.03`;
- максимум 3 шага;
- наблюдаемость `100%`, `75%`, `50%`;
- источники в основном режиме сохраняются среди наблюдаемых кандидатов;
- ложноположительный шум проверяется отдельно.

## 2. Реализованные модели

### Joint Source-Count GCN

Собственная архитектура на базе стандартных `GCNConv` из PyTorch Geometric:

- двухслойный GCN-backbone;
- узловая голова с одним source logit на узел;
- count-head для классов `1`, `2`, `3`;
- общие mean/max pooling по графу и observed nodes.

Изначальная функция потерь:

```text
L = L_source
  + lambda_count * L_count
  + lambda_consistency * L_consistency
```

В финальной рабочей конфигурации consistency-loss отключен: `lambda_consistency=0.0`.

### Node-only GCN

Та же узловая GCN без count-head. Для estimated-k используется threshold, выбранный по validation.

### Классические baseline

- Uniform;
- Degree;
- Multi-Jordan.

## 3. Фактические результаты основной серии

Завершены три seed для Joint без consistency и Node-only:

```text
7026, 7027, 7028
```

### Joint без consistency

Средние estimated-k результаты по трем seed:

- F1: `0.3467`;
- precision: `0.3631`;
- recall: `0.3482`;
- count accuracy: `0.6266`;
- count MAE: `0.4339`;
- exact set accuracy: `0.0657`;
- symmetric graph distance: `1.1583`.

95% t-интервалы для среднего F1: примерно `0.3349-0.3586`.

Качество по числу источников:

- `k=1`: F1 около `0.127`;
- `k=2`: F1 около `0.404`;
- `k=3`: F1 около `0.509`.

### Node-only thresholded

Средние estimated-k результаты:

- F1: `0.3695`;
- precision: `0.3729`;
- recall: `0.4167`;
- count accuracy: `0.4211`;
- count MAE: `0.7968`;
- exact set accuracy: `0.0295`;
- symmetric graph distance: `1.0775`.

### Смысл сравнения

Node-only лучше по частичному совпадению и средней близости к источникам.

Joint лучше оценивает количество источников и примерно в 2,2 раза чаще полностью восстанавливает множество источников.

В oracle-k режиме GCN дают F1 около `0.36`, то есть узловая локализация заметно лучше классических baseline:

- Degree: `0.1071`;
- Uniform: `0.1714`;
- Multi-Jordan: `0.2735`;
- Joint oracle-k: около `0.362`;
- Node-only oracle-k: около `0.359`.

Multi-Jordan имеет меньшую среднюю graph distance, около `0.854`, поэтому в отчете надо отдельно обсуждать F1 и геометрическую близость.

## 4. Проверка consistency-loss

Validation-only tuning на seed 7026:

| `lambda_consistency` | Validation F1 | Count accuracy | Count MAE |
|---:|---:|---:|---:|
| `0.1` | `0.355239` | `0.622623` | `0.464965` |
| `0.01` | `0.356373` | `0.567067` | `0.524024` |
| `0.0` | `0.355889` | `0.628128` | `0.424424` |

Разница F1 между `0.01` и `0.0` всего около `0.00048`, при этом `0.0` лучше по count accuracy и count MAE. Поэтому выбран `lambda_consistency=0.0`, а consistency-loss оформляется как отрицательная абляция.

## 5. Robustness и перенос

Robustness для Joint без consistency, seed 7026:

- при 100% наблюдаемости и 0% шума F1: `0.3188`;
- при 75% наблюдаемости и 0% шума F1: `0.3483`;
- при 50% наблюдаемости и 0% шума F1: `0.4091`;
- при 10% шума F1: `0.2158`, `0.2629`, `0.3372` для 100%, 75%, 50% наблюдаемости.

Улучшение при меньшей наблюдаемости не является настоящей монотонной устойчивостью: источники гарантированно сохраняются, а candidate set уменьшается. Это ограничение основного протокола нужно явно описать.

IC -> SI:

- IC F1: `0.3522`;
- SI F1: `0.3463`;
- IC count accuracy: `0.6306`;
- SI count accuracy: `0.6321`.

Смена процесса не вызвала существенного падения.

Facebook -> email-Eu-core без дообучения:

- Facebook F1: `0.3522`;
- email F1: `0.1744`;
- email count accuracy: `0.3444`;
- email count MAE: `0.9556`;
- email graph distance: `1.7704`.

Перенос на другую топологию заметно хуже, но это честно показывает domain shift.

## 6. Текущая оценка продукта

Технически система работает end-to-end:

- генерирует каскад;
- формирует наблюдение;
- загружает checkpoint;
- оценивает источники;
- определяет количество;
- показывает результат в приложении;
- сохраняет метрики и checkpoint.

Предсказательная способность умеренная, а не высокая:

- количество источников определяется примерно в 63% случаев Joint;
- полное множество источников угадывается примерно в 6,6% случаев;
- модель часто находит близкую область, но не обязательно точный узел;
- качество заметно падает на другой топологии и при ложноположительном шуме.

Корректная формулировка результата:

> Разработана работающая GCN-система для оценки количества и локализации нескольких источников информационной диффузии на известном социальном графе. Внутри исходной топологии система превосходит классические baseline-методы, однако точность зависит от числа источников, шума наблюдений и различия топологий.

## 7. Почему модель можно улучшить

Текущая модель ограничена:

- всего двумя входными признаками;
- двумя GCN-слоями;
- локальной узловой головой без явного global context;
- BCE-loss без ranking-компоненты;
- одной моделью для `k=1`, `k=2`, `k=3`.

Главная слабость - `k=1`, где F1 около `0.13`.

## 8. Варианты улучшения

### Вариант A. Новые структурные признаки

Добавить признаки, рассчитанные только из графа и наблюдаемого снимка:

```text
observed_infected
log_degree_normalized
infected_neighbor_count
infected_neighbor_fraction
uninfected_neighbor_count
uninfected_neighbor_fraction
local_observed_density
distance_to_observation_boundary
```

Нельзя добавлять ID пользователя, истинное время заражения или истинный source flag.

Ожидаемый эффект: меньше ложных кандидатов и улучшение особенно для `k=1`.

### Вариант B. Третий residual GCN-слой

Текущий процесс моделируется до 3 шагов, а backbone имеет 2 слоя. Можно проверить:

```text
2 слоя против 3 слоев
```

Желательна residual-связь:

```text
h1 = GCN1(x)
h2 = GCN2(h1) + h1
h3 = GCN3(h2) + h2
```

### Вариант C. Global-context узловая голова

Сейчас source score строится из локального hidden узла. Улучшенный вариант:

```text
node_hidden + global_observed_pool + local_features
    -> source score
```

Это позволит оценивать узел с учетом всей формы наблюдаемого каскада.

### Вариант D. Ranking-loss

Добавить к BCE loss требование:

```text
score(true source) > score(false candidate)
```

Например:

```text
L = L_BCE + lambda_rank * L_rank
```

Это должно улучшить top-k F1 и exact set accuracy.

### Вариант E. Гибрид GCN + Multi-Jordan

Объединить neural score и graph-centrality score:

```text
final_score = alpha * neural_score
            + (1 - alpha) * jordan_score
```

`alpha` подбирается только по validation.

Плюс: вероятное улучшение практической локализации.

Минус: итоговый метод будет гибридным, а не чистой GCN.

### Вариант F. Более информативные каскады

Создать отдельный dataset v2 с:

- `max_steps=4` или `5`;
- немного большими вероятностями передачи;
- большим количеством каскадов среднего размера;
- более равномерным распределением расстояний источников.

Старый dataset нельзя удалять. Новый протокол должен сравниваться отдельно, чтобы не создавать искусственно легкий test.

### Вариант G. Увеличение train до 20-30 тысяч

Имеет смысл только если learning curve показывает рост validation F1 при переходе от 2 500 к 5 000 и 9 990 примерам. Если validation вышел на плато, увеличение данных не решит проблему.

### Вариант H. Специализированные головы по k

Сначала count-head определяет `k`, затем отдельная локализационная голова учитывает это значение. Вариант мощный, но более сложный и рискованный.

## 9. Рекомендуемый порядок улучшения

Не менять всё сразу. Предлагаемый порядок:

1. Добавить структурные признаки.
2. Добавить третий residual GCN-слой.
3. Сделать узловую голову global-context.
4. Обучить улучшенный Node-only.
5. Обучить улучшенный Joint без consistency.
6. Сравнить со старой моделью на том же test split.
7. Если есть улучшение, проверить ranking-loss.
8. Повторить лучшую конфигурацию с тремя seed.
9. Сохранить старую модель как baseline версии 1.

Целевые ориентиры:

```text
F1:                 0.45-0.55
count accuracy:     0.70+
exact set accuracy: 0.10-0.20
graph distance:     0.8-1.0
```

Это цели для проверки, а не гарантии.

## 10. Что показывать комиссии

Сравнение версий:

| Версия | Роль |
|---|---|
| Degree / Multi-Jordan | классические baseline |
| Текущая GCN | исходная нейросетевая модель |
| Node-only | нейросетевой baseline |
| Joint без consistency | текущая основная рабочая модель |
| Улучшенная Joint | итоговая модель после обоснованных изменений |

Научно честный сценарий:

1. показать исходные результаты;
2. выявить слабость `k=1` и count estimation;
3. добавить признаки и глобальный контекст;
4. проверить улучшение на том же test protocol;
5. сохранить старую модель для честного сравнения;
6. отдельно показать robustness и transfer limitations.
