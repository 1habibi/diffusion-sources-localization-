# Состояние модели и план улучшений

Документ предназначен для переноса контекста в новый чат. Он фиксирует фактические результаты основной серии и варианты улучшения модели.

## 1. Что уже сделано

Реализована система локализации от одного до трех источников информационной диффузии на известном графе социальной сети.

Pipeline:

```text
Facebook-граф + неполный снимок каскада
        -> признаки узлов
        -> GCN
        -> scores источников + оценка k
        -> множество предполагаемых источников
```

Основной граф - SNAP ego-Facebook:

- 4 039 узлов;
- 88 234 неориентированных ребра;
- средняя степень около 43,69.

Основной датасет полусинтетический: топология реальная, а IC-каскады, источники и наблюдения сгенерированы программно.

Размеры датасета:

- train: 9 990;
- validation: 1 998;
- test: 1 998.

Распределение сбалансировано по `k=1,2,3`, вероятностям IC и долям наблюдаемости.

Основные условия:

- Independent Cascade;
- вероятности передачи `0.01`, `0.02`, `0.03`;
- максимум 3 шага;
- наблюдаемость `100%`, `75%`, `50%`;
- источники в основном режиме сохраняются среди наблюдаемых кандидатов;
- ложноположительный шум проверяется отдельно.

## 2. Реализованные модели

### Joint Source-Count GCN

Собственная архитектура на базе стандартных `GCNConv` из PyTorch Geometric:

- двухслойный GCN-backbone;
- узловая голова с одним source logit на узел;
- count-head для классов `1`, `2`, `3`;
- общие mean/max pooling по графу и observed nodes.

Изначальная функция потерь:

```text
L = L_source
  + lambda_count * L_count
  + lambda_consistency * L_consistency
```

В финальной рабочей конфигурации consistency-loss отключен: `lambda_consistency=0.0`.

### Node-only GCN

Та же узловая GCN без count-head. Для estimated-k используется threshold, выбранный по validation.

### Классические baseline

- Uniform;
- Degree;
- Multi-Jordan.

## 6. Текущая оценка продукта

Технически система работает end-to-end:

- генерирует каскад;
- формирует наблюдение;
- загружает checkpoint;
- оценивает источники;
- определяет количество;
- показывает результат в приложении;
- сохраняет метрики и checkpoint.

Предсказательная способность умеренная, а не высокая:

- количество источников определяется примерно в 63% случаев Joint;
- полное множество источников угадывается примерно в 6,6% случаев;
- модель часто находит близкую область, но не обязательно точный узел;
- качество заметно падает на другой топологии и при ложноположительном шуме.

Корректная формулировка результата:

> Разработана работающая GCN-система для оценки количества и локализации нескольких источников информационной диффузии на известном социальном графе. Внутри исходной топологии система превосходит классические baseline-методы, однако точность зависит от числа источников, шума наблюдений и различия топологий.

## 7. Почему модель можно улучшить

Текущая модель ограничена:

- всего двумя входными признаками;
- двумя GCN-слоями;
- локальной узловой головой без явного global context;
- BCE-loss без ranking-компоненты;
- одной моделью для `k=1`, `k=2`, `k=3`.

Главная слабость - `k=1`, где F1 около `0.13`.

## 8. Границы v2 и неизменяемые правила

`v2` делится на две самостоятельные постановки:

| Режим | Назначение | Данные для прямого сравнения |
|---|---|---|
| `snapshot-v2` | улучшение текущей задачи по одному неполному снимку | те же Facebook train/validation/test, что у `v1` |
| `temporal-v2` | отдельный эксперимент с 2-3 последовательными снимками | новый, независимо версионируемый temporal-датасет |

Основным результатом следующей версии считается `snapshot-v2`: он не меняет доступную модели информацию и поэтому допускает честное сравнение с `v1`. `temporal-v2` нельзя выдавать за архитектурное улучшение `v1`, потому что временная последовательность делает вход более информативным.

Для обоих режимов действуют правила:

- `v1`, его конфигурации, splits, checkpoints и отчеты не перезаписываются;
- архитектура и гиперпараметры выбираются только по validation;
- существующий test используется для сопоставимости, но не для выбора решений;
- каждый вариант меняет ровно один фактор относительно текущего победителя;
- неудачные и нейтральные абляции фиксируются наравне с успешными;
- после последовательной серии для финального победителя выполняются leave-one-component-out абляции, чтобы проверить вклад компонентов с учетом взаимодействий;
- ID узла, истинный source flag, истинное время заражения и иная недоступная при inference информация запрещены.

Этот документ является планом. Реализация `v2`, новые конфигурации и обучение на текущем этапе не начинаются.

## 9. Целевая архитектура snapshot-v2

```text
граф + один неполный снимок
        -> структурные признаки узлов
        -> 2- или 3-слойный residual GCN
        -> локальные embeddings
        + global context наблюдаемого каскада
        -> count-head: k in {1, 2, 3}
        -> source-head_k1 / source-head_k2 / source-head_k3
        -> preliminary scores
        -> безопасный shortlist (опциональная абляция)
        -> ranking-head
        -> top-k источников
```

Архитектура должна быть одной конфигурируемой моделью, а не набором почти одинаковых реализаций. Число слоев, группы признаков, global context, specialized heads, ranking-loss, Jordan-признак и shortlist должны включаться независимо через конфигурацию.

### 9.1. Структурные признаки

Признаки рассчитываются только по известному графу и доступному снимку. Их следует вводить группами, чтобы измерить вклад и контролировать избыточность.

**Базовые признаки `v1`:**

- `observed_infected`;
- `log_degree_normalized`.

**Локальная структура снимка:**

- число и доля наблюдаемых зараженных соседей;
- число и доля ненаблюдаемых/незараженных соседей;
- локальная плотность наблюдаемой зараженной окрестности.

**Положение относительно каскада:**

- расстояние до границы наблюдаемой зараженной области;
- среднее и максимальное расстояние до наблюдаемых зараженных узлов;
- эксцентриситет внутри индуцированной наблюдаемой области.

**Глобальные скаляры, повторяемые для кандидатов:**

- размер наблюдаемого каскада;
- размер candidate set;
- доля наблюдаемых зараженных узлов среди кандидатов;
- плотность индуцированной наблюдаемой области.

При реализации `S1c` дополнительно проверены число связных компонент наблюдаемой области и доля крупнейшей компоненты. Feature-only диагностика подтвердила, что в основном протоколе `candidate_count` точно равен `observed_count`, а `observed_candidate_fraction` постоянно равен `1.0`; эти два признака исключены до обучения. Итоговая `S1c` добавляет четыре независимых скаляра: нормированный размер наблюдаемого множества, плотность, нормированное число компонент и долю крупнейшей компоненты.

Граница определяется как наблюдаемый зараженный узел, имеющий хотя бы одного соседа вне наблюдаемого зараженного множества. Расстояние до пустой границы и недостижимые расстояния должны иметь заранее зафиксированное capped-значение и отдельный индикатор отсутствия значения. Count-признаки нормализуются доступными характеристиками фиксированной топологии, distance-признаки — заранее заданным cap. Если позднее применяется статистическая стандартизация, ее параметры оцениваются только по train; статистики validation/test/holdout не используются.

Предварительная диагностика `S1b` на train/validation показала, что при текущем протоколе почти каждый наблюдаемый кандидат сам является границей: `distance_to_observation_boundary` меняется только примерно в `2%` примеров (`std≈0.003`), а индикатор отсутствующей границы всегда равен нулю. Поэтому оба граничных признака исключены из GPU-конфигурации `S1b` до обучения и зафиксированы как вырожденные для данного протокола. В `S1b` остаются среднее/максимальное расстояние до наблюдаемого множества и эксцентриситет в индуцированной наблюдаемой области.

Статические графовые величины можно кэшировать один раз. Признаки, зависящие от снимка, вычисляются отдельно для каждого примера. Перед обучением проверяются конечность значений, отсутствие target leakage и идентичность преобразований на всех splits.

### 9.2. Residual GCN

Третий слой является гипотезой, а не следствием равенства `max_steps=3`. Сравнение проводится при одинаковых hidden dimension, optimizer, budget и seed:

```text
2-layer backbone
vs
h1 = GCN1(x)
h2 = GCN2(h1) + Proj2(h1)
h3 = GCN3(h2) + Proj3(h2)
```

`Proj` — identity при совпадении размерностей и обучаемая линейная проекция иначе. Для честной проверки отдельно фиксируются число параметров и время эпохи; возможное улучшение не должно объясняться только существенно большим budget.

### 9.3. Global-context голова

Для каждого кандидата формируется контекст:

```text
[node_embedding,
 mean/max pool observed nodes,
 mean/max pool candidate nodes,
 global cascade scalars]
    -> source score
```

Pooling использует маски конкретного примера, не смешивает графы в batch и отклоняет пример с пустой обязательной маской. В изолированной абляции `S2` меняется только source-head; существующая count-head сохраняет прежний all-node/observed-node pooling. Это позволяет отнести возможную разницу именно к ранжированию кандидатов с глобальным контекстом.

### 9.4. Специализированные головы для k=1/2/3

После общей части используются три source-head:

```text
source_head_k1, source_head_k2, source_head_k3
```

На train применяется голова истинного `k`; на inference — голова предсказанного count-head значения. Обязательны два режима оценки:

- `estimated-k` показывает работу полной системы;
- `oracle-k` использует истинное `k` и отделяет ошибку локализации от ошибки count-head.

Отдельно публикуются F1 и Hit-метрики для `k=1`, `k=2`, `k=3`. Главная проверяемая гипотеза — заметное улучшение слабого режима `k=1` без деградации `k=2/3`.

Локальная реализация возвращает матрицу source logits `[num_nodes, 3]`. BCE и выключенный в основной конфигурации consistency-компонент маршрутизируются по истинному `k` каждого графа только во время обучения/расчета loss. В `estimated-k` оценке столбец выбирается исключительно прогнозом count-head; истинное `k` используется только в явно названном `oracle-k` режиме. Count-head, backbone и входные признаки на шаге `S4` не меняются.

### 9.5. Ranking-loss

Функция потерь планируется как:

```text
L = L_BCE + lambda_count * L_count + lambda_rank * L_rank
```

`L_rank` сравнивает каждый истинный источник только с допустимыми ложными кандидатами того же каскада. Для ограничения числа пар применяются negative sampling и hard negatives с высокими текущими scores. Пары между разными примерами запрещены. `lambda_rank`, число negatives и доля hard negatives выбираются по validation; `lambda_rank=0` является обязательной контрольной точкой.

Реализованный `L_rank` использует smooth pairwise objective `softplus(score_negative - score_positive)`. Перед ним specialized logits `S4` маршрутизируются по истинному `k` графа так же, как BCE. На train после обязательной hard-части оставшиеся negatives семплируются генератором PyTorch, состояние которого уже входит в resume-checkpoint; при повторной оценке train/validation применяется детерминированная выборка, чтобы diagnostic loss не зависел от нового RNG. При `lambda_rank=0` ranking-ветка полностью пропускается и не меняет ни вычисления, ни состояние RNG контрольного варианта.

Начальная конфигурация `S5` использует `lambda_rank=0.2`, не более 8 negatives на истинный источник и hard fraction `0.5`. Это стартовая точка, а не принятое значение: сравнение проводится с явным `S5-control` при `lambda_rank=0`, после чего ограниченная сетка разрешена только по validation.

### 9.6. Jordan-признак и гибридная абляция

Нормированный Multi-Jordan score сначала проверяется как отдельный входной признак. Это основной способ использовать сигнал классического метода, который у `v1` лучше по graph distance.

Реализованный `multi_jordan_rank_normalized` строит полный жадный порядок допустимых кандидатов по тому же лексикографическому критерию, что baseline: минимизируются максимальное расстояние наблюдаемого узла до ближайшего уже выбранного центра, затем сумма расстояний и node ID. Первый кандидат получает `1`, последний `0`, промежуточные — линейно нормированный ранг. Поэтому top-`k` признака в точности совпадает с существующим Multi-Jordan для `k=1/2/3`, но при построении не используются истинные источники или истинное `k`. Первоначальный вариант, являвшийся линейной комбинацией уже имеющихся mean/max distance, был отклонён до GPU как информационно избыточный.

Смешивание после модели:

```text
final_score = alpha * neural_score + (1 - alpha) * jordan_score
```

не входит в основную архитектуру и допускается только как отдельная вторичная абляция. `alpha` выбирается только по validation; результаты нельзя смешивать с результатами чистой нейросетевой модели.

### 9.7. Безопасный shortlist

Shortlist — опциональный двухэтапный inference, а не безусловное удаление кандидатов:

1. preliminary head оценивает всех допустимых кандидатов;
2. если их не больше `M`, ranking-head получает всех;
3. иначе ranking-head получает top-`M`;
4. при любой ошибке/пустом shortlist выполняется fallback на полный candidate set.

`M` выбирается по validation из заранее заданной сетки. Shortlist разрешается включать в финальную модель, только если одновременно выполнены условия:

- micro candidate recall истинных источников не ниже `0.95`;
- candidate recall отдельно для каждого `k` не ниже `0.95`;
- нижняя граница 95% bootstrap CI для candidate recall не ниже `0.93`;
- F1 или latency улучшаются относительно той же модели без shortlist;
- на holdout shortlist не перенастраивается и всегда сохраняется полный-score fallback.

Если условия не выполнены, shortlist фиксируется как отрицательная абляция и не применяется.

Реализация `S7` добавляет линейную preliminary-head поверх того же node/global source context. Её вход отсоединён от autograd-графа (`detach`), поэтому preliminary BCE обучает только эту голову и не изменяет backbone, count-head или специализированные ranking-head текущего победителя. Полный scoring остаётся контрольным режимом того же checkpoint. В shortlist-режиме preliminary-head оценивает всех кандидатов, а дорогие ranking-head вычисляются только для top-`M`; logits остальных узлов получают `-inf` и не могут быть выбраны.

Сетка `M=[8,12,16,24,32]` фиксируется до полного validation-запуска. Для каждого `M` сохраняются micro recall, recall по `k`, bootstrap CI, full/shortlist F1, end-to-end latency, доля сокращённых кандидатов и fallback rate. Ошибочные, нечисловые или пустые preliminary scores включают полный candidate fallback. Решение принимает только validation evaluator; если ни один `M` не проходит все пороги, `selected_size=null`, решение равно `reject_shortlist`, а финальная модель использует полный scoring.

## 10. Последовательный план изолированных абляций snapshot-v2

Все exploratory-запуски выполняются на одном заранее выбранном development seed и одинаковом budget. После каждого шага новый вариант сравнивается с текущим победителем; в следующий шаг переносится только вариант, выбранный по заранее заданному validation score. Test и final holdout закрыты.

Основной validation score — macro F1 по примерам в `estimated-k` режиме. При разнице менее `0.005` выбирается более простая модель; tie-breakers по порядку: F1 для `k=1`, count accuracy, exact set accuracy, symmetric graph distance.

| ID | Единственное изменение | Контроль |
|---|---|---|
| `S0` | воспроизвести `v1 Joint` | неизменяемый baseline |
| `S1a` | добавить локальные structural features | `S0` |
| `S1b` | добавить distance/position features к победителю | текущий победитель |
| `S1c` | добавить global scalar features к победителю | текущий победитель |
| `S2` | заменить локальную source-head на global-context head | текущий победитель |
| `S3` | заменить 2 слоя на 3 residual слоя | текущий победитель |
| `S4` | включить specialized heads для `k=1/2/3` | текущий победитель |
| `S5` | включить ranking-loss | тот же вариант с `lambda_rank=0` |
| `S6` | добавить нормированный Jordan-признак | текущий победитель |
| `S7` | включить safe shortlist | тот же вариант без shortlist |

Порядок фиксирован для воспроизводимости, но отклоненный шаг не становится частью следующего варианта. После выбора кандидата `snapshot-v2` выполняется `leave-one-out` для каждого оставленного компонента. Компонент сохраняется в финале, только если его удаление не улучшает validation score и его роль можно объяснить результатами.

Локальная реализация `S2` сохраняет двухслойный backbone и прежнюю count-head. Единственное архитектурное изменение находится в source-head: для каждого кандидата она объединяет его node embedding, mean/max pooling по observed set, mean/max pooling по candidate set и четыре выбранных в `S1c` graph-level скаляра. Режим `local` остается значением по умолчанию, поэтому загрузка и воспроизведение checkpoints `v1` не требуют новой головы.

В локальной реализации `S3` первый GCN-слой переводит входные признаки в hidden space, после чего второй и третий GCN-слои работают в одной размерности и получают additive skip-связи. По отношению к `S2` не меняются признаки, global-context source-head, count-head, loss или training budget. Режим `plain_2` остается значением по умолчанию для обратной совместимости с `v1`; residual-вариант включается только явным `backbone_mode: residual_3`.

Для шага, прошедшего первичный отбор, желательно выполнить подтверждение минимум на втором seed до дорогой финальной серии. Полный перебор комбинаций не проводится; все проверенные конфигурации и причины принятия/отклонения записываются в реестр экспериментов.

## 11. Финализация snapshot-v2 и закрытый final holdout

Существующий test уже использовался для диагностики `v1`, включая анализ candidate set, и поэтому не является полностью слепым по отношению к проектированию `v2`. До начала реализации необходимо создать дополнительный `snapshot_final_holdout`:

- протокол генерации совпадает с основным Facebook snapshot-протоколом;
- simulation/observation seeds не пересекаются с train/validation/test;
- размер, seed manifest, checksum файлов и версия генератора фиксируются до разработки;
- labels и агрегаты holdout не просматриваются до freeze модели;
- holdout не участвует в feature normalization, tuning, early stopping или выборе checkpoint;
- до открытия фиксируются config checksum, checkpoint checksum, кодовая revision и скрипт оценки;
- holdout открывается один раз для финальных `v1` и `snapshot-v2` checkpoints; повторная настройка после открытия запрещена.

Финальная процедура:

1. заморозить победившую конфигурацию по validation;
2. обучить ее на seed `7026`, `7027`, `7028` без изменения budget;
3. агрегировать validation и существующий test для сопоставимости с `v1`;
4. до открытия holdout зафиксировать все checksums;
5. один раз оценить `v1 Joint`, `v1 Node-only` и `snapshot-v2` на final holdout;
6. повторить robustness и transfer только для замороженного победителя;
7. опубликовать среднее по seed, разброс между обучениями и paired bootstrap CI по примерам.

## 12. Метрики и критерии успеха

Обязательные метрики для validation, test и final holdout:

- precision, recall и F1 в `estimated-k` и `oracle-k` режимах;
- count accuracy и count MAE;
- exact set accuracy;
- symmetric graph distance;
- результаты отдельно для `k=1`, `k=2`, `k=3` и диапазонов candidate set;
- `Hit@1-hop` и `Hit@2-hop`;
- candidate recall и latency, если используется shortlist.

Для радиусных метрик для каждого истинного источника считается минимальное расстояние до любого предсказанного источника. `Hit@r-hop` — доля истинных источников, для которых это расстояние не превышает `r`; затем она macro-усредняется по каскадам. Поэтому `Hit@0-hop` совпадает с source recall, а `Hit@1-hop` и `Hit@2-hop` показывают практически близкую локализацию. Дополнительно можно публиковать `All-Hit@r-hop` — долю каскадов, где условие выполнено для всех истинных источников.

Минимальный критерий заметного успеха `snapshot-v2` на закрытом holdout:

- прирост macro F1 относительно `v1 Joint` не менее `0.03`;
- 95% paired bootstrap CI разности F1 не включает `0`;
- F1 для `k=1` растет не менее чем на `0.05`;
- count accuracy не ухудшается более чем на `0.02`;
- ни для `k=2`, ни для `k=3` F1 не ухудшается более чем на `0.02`.

Целевые, но не гарантированные ориентиры:

```text
macro F1:           >= 0.45
count accuracy:     >= 0.70
exact set accuracy: >= 0.12
Hit@1-hop:          >= 0.70
graph distance:     <= 1.00
```

Результат может считаться полезным инженерным компромиссом и без выполнения всех ориентиров, если выполнен минимальный критерий и улучшение не получено ценой неприемлемой latency/памяти. Если paired CI включает ноль, вывод формулируется как отсутствие подтвержденного улучшения.

## 13. Отдельный режим temporal-v2

`temporal-v2` начинается только после freeze и оценки `snapshot-v2`. Для него создаются собственные `train/validation/test/final_holdout`, конфигурации, каталоги и таблицы.

Вход содержит 2-3 упорядоченных неполных снимка после начала распространения:

```text
snapshot(t1) -> snapshot(t2) -> snapshot(t3),  0 < t1 < t2 < t3
```

Защита от утечки:

- снимок в `t=0` не предоставляется;
- истинное время заражения, source flag и порядок активации узлов не передаются;
- источник не кодируется особым значением и не сохраняется искусственно в каждом снимке;
- правила пропусков и ложноположительного шума фиксируются до генерации;
- splits разделяются по seeds каскадов до формирования снимков, чтобы версии одного каскада не попали в разные splits;
- нормализация и tuning используют только temporal train/validation;
- candidate policy и ее recall публикуются явно.

Минимальные абляции temporal-режима:

1. лучший `snapshot-v2` только по последнему снимку;
2. тот же backbone с несколькими снимками без отдельного temporal encoder;
3. temporal aggregation/encoder;
4. 2 снимка против 3 снимков;
5. при необходимости — temporal ranking-loss.

Успех temporal-режима измеряется относительно `snapshot-v2`, переоцененного на последнем снимке того же temporal-протокола. Числа temporal и исходного snapshot test нельзя сравнивать как результаты одного датасета.

## 14. Contingency-план, если v2 не улучшит результат

Если `snapshot-v2` не выполнит минимальный критерий, нельзя подбирать модель по final holdout или скрывать отрицательный результат. Действия выполняются последовательно:

1. **Проверить корректность эксперимента:** leakage-аудит, маски batch, feature scaling, candidate recall, одинаковый budget, воспроизводимость `S0`, корректность `estimated-k/oracle-k` и Hit-метрик.
2. **Локализовать ограничение:** сравнить oracle-k с estimated-k, результаты по `k` и размеру candidate set, calibration count-head, learning curves и ошибки shortlist. Это определит, проблема в count estimation, локализации, данных или optimization.
3. **Выбрать простейший устойчивый вариант:** если сложная модель не лучше, оставить лучший подтвержденный промежуточный вариант (например, только structural features + global context) либо `v1` как итоговую snapshot-модель.
4. **Проверить бюджет данных:** строить learning curve на 2 500/5 000/9 990 примерах. Увеличивать train до 20-30 тысяч только при продолжающемся росте validation F1.
5. **Проверить постановку данных отдельно:** более длинные/информативные каскады, отсутствие искусственного сохранения источников и баланс расстояний между источниками оформлять как новый dataset protocol, а не как улучшение на старом test.
6. **Провести temporal-v2 как отдельный эксперимент:** временная информация может дать прирост, но не заменяет отрицательный вывод по snapshot-v2.
7. **Зафиксировать научный вывод:** архитектурные усложнения не дали статистически подтвержденного прироста при одном неполном снимке; описать отрицательные абляции, ограничения идентифицируемости и наиболее устойчивый baseline.

Один дополнительный цикл гипотез после аудита допустим только с новой заранее сформулированной причиной и снова выбирается по validation. Final holdout после открытия не переиспользуется; для нового цикла требуется новый независимо сгенерированный holdout.

## 15. Материалы для итогового сравнения

Основная таблица snapshot-режима должна включать:

| Версия | Роль |
|---|---|
| Uniform / Degree / Multi-Jordan | классические baseline |
| `v1 Node-only` | нейросетевой baseline |
| `v1 Joint` | текущая основная модель |
| промежуточные `S1-S7` | изолированные абляции по validation/test |
| `snapshot-v2` | замороженный победитель |

Логика представления результата:

1. диагностика `v1` выявляет слабость `k=1` и зависимость от candidate set;
2. каждая гипотеза проверяется отдельно;
3. финальная snapshot-модель сравнивается на прежнем test и новом закрытом holdout;
4. Hit-метрики отделяют точную идентификацию от близкой локализации;
5. temporal-режим показывается отдельной постановкой;
6. robustness, transfer и отрицательные абляции сохраняются в выводах.
