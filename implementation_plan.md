# План реализации системы локализации источников диффузии

Этот документ определяет порядок разработки кода на основе `explaining.md`. Основной результат проекта - воспроизводимая система, которая по графу и неполному снимку диффузии локализует неизвестное множество из 1-3 источников и оценивает их количество.

Работа выполняется последовательно: сначала инфраструктура и симулятор, затем данные и baseline-методы, после этого нейросетевые модели, эксперименты и демонстрационное приложение. Переходить к следующему крупному этапу следует только после выполнения проверок текущего.

## 2. Система тестирования и контроль качества

Тестирование создается параллельно с кодом, а не после завершения моделей. Использовать три уровня:

- unit-тесты для графов, симулятора, наблюдений, функций потерь и метрик;
- integration-тесты полного пути `граф -> каскад -> наблюдение -> признаки -> модель -> метрики`;
- smoke-тесты CLI-скриптов обучения, оценки и Streamlit на маленьком Karate Club.

В pytest добавить общие фикстуры маленьких графов: путь, дерево, цикл и несвязный граф до preprocessing. Для случайных алгоритмов проверять инварианты и воспроизводимость по seed, а не конкретные случайные значения. Для метрик использовать вручную рассчитанные примеры с полным совпадением, частичным совпадением и отсутствием совпадений.

Автоматическая проверка должна включать:

```text
pytest
    -> unit
    -> integration
    -> smoke
    -> отчет о покрытии
```

Минимальная цель покрытия - 80% для `diffusion.py`, `observations.py`, `losses.py` и `metrics.py`. Покрытие не заменяет содержательные тесты, но не позволяет критической логике остаться без проверки. Ошибка любого обязательного теста блокирует массовую генерацию данных и финальные эксперименты.

**Результат этапа:** одна команда запускает всю тестовую систему, а краткий отчет о количестве и составе тестов можно включить в практическую главу ВКР.

## 3. Графы и подготовка топологий

В `graphs.py` реализовать загрузку edge list, удаление петель, преобразование графа в неориентированный вид, выделение крупнейшей связной компоненты и перенумерацию узлов в диапазон `0..N-1`. Там же реализовать генерацию Karate Club, Erdős-Rényi и Barabási-Albert.

Для каждого графа сохранять:

- обработанный edge list или `edge_index`;
- соответствие исходных и внутренних ID;
- число узлов и ребер;
- среднюю степень, плотность, число компонент и диаметр, если его расчет допустим по времени.

Сначала проверить код на Karate Club. После этого добавить загрузку SNAP ego-Facebook и email-Eu-core. Скрипт скачивания не должен молча перезаписывать существующие файлы.

**Проверки:** после обработки отсутствуют петли, граф не содержит изолированных компонент вне выбранной крупнейшей компоненты, ID непрерывны, повторная загрузка дает тот же граф.

## 4. Многоисточниковый симулятор IC

В `diffusion.py` реализовать `simulate_ic(G, sources, p, max_steps, rng)`. Все источники активируются на такте 0. Каждый вновь зараженный узел получает одну попытку заразить каждого восприимчивого соседа с вероятностью `p`.

Результат симуляции должен содержать:

- множество источников;
- время заражения каждого зараженного узла;
- историю новых заражений по тактам;
- итоговое множество зараженных;
- параметры `p`, `max_steps` и seed.

Отдельно реализовать выбор `k` источников с контролем их степени и попарного расстояния. Генератор должен уметь создавать близкие, средние и удаленные наборы источников, а не выбирать только удобные случаи.

**Обязательные тесты:** при `p=0` заражены только источники; при `p=1` на связном графе и достаточном числе тактов заражаются все достижимые узлы; один и тот же seed дает одинаковую историю; порядок источников не влияет на результат.

## 5. Формирование наблюдаемого снимка

В `observations.py` отделить истинный каскад от данных, доступных модели. Функция `observe_cascade(...)` должна поддерживать:

- долю наблюдаемых зараженных: 100%, 75% и 50%;
- обязательное сохранение всех источников в основном режиме;
- добавление ложноположительных узлов;
- отдельный режим со скрытым источником;
- формирование маски допустимых кандидатов.

В основном режиме кандидаты равны наблюдаемым зараженным узлам. При ложноположительном шуме ложные узлы также входят в кандидаты. Для эксперимента со скрытым источником кандидатами становятся все узлы графа, и для этого режима позднее обучается отдельная модель.

Сохранять `simulation_seed` и `observation_seed` отдельно. Все варианты наблюдения одного истинного каскада должны относиться к одному split.

**Результат этапа:** для любого каскада можно воспроизводимо получить чистый, неполный и зашумленный снимки без утечки истинных меток в признаки.

## 6. Признаки и формат датасета

В `features.py` реализовать основной набор признаков:

```text
[observed_infected, log_degree_normalized]
```

Нормированная степень рассчитывается отдельно для каждого графа. ID узла и обучаемые embeddings конкретных пользователей не использовать, чтобы модель не запоминала вершины Facebook.

В `dataset.py` определить единый объект примера, содержащий:

- `graph_id` и ссылку на общую топологию;
- матрицу узловых признаков;
- маску кандидатов;
- бинарный вектор источников;
- истинное количество `k`;
- параметры симуляции и наблюдения;
- идентификаторы split и seed.

Топология хранится один раз на граф, а не копируется для каждого каскада. Сначала создать пилот из 500 каскадов. После анализа размеров каскадов зафиксировать `p`, допустимые такты наблюдения, фильтры и итоговые размеры выборок.

Начальная цель для Facebook: 10 000 train, 2 000 validation и 2 000 test. В каждом split должно быть примерно одинаковое число примеров для `k=1`, `k=2` и `k=3`.

**Проверки:** отсутствуют пересечения истинных каскадов между split; распределения `k`, степени и расстояний источников сохраняются в отчете; одинаковая конфигурация и seed создают одинаковый датасет.

## 7. Метрики и классические baseline-методы

Метрики следует реализовать до нейросетевого обучения, чтобы все методы оценивались одинаково. В `metrics.py` добавить:

- precision, recall и F1 для каждого каскада;
- macro-F1;
- exact set accuracy;
- count accuracy и count MAE;
- расстояние от истинных источников до предсказанного множества и обратно;
- PR-AUC по узловым scores.

В `baselines.py` реализовать:

- `UniformCandidates`: случайный выбор `k` кандидатов с усреднением по фиксированным seed;
- `DegreeCandidates`: выбор кандидатов с максимальной степенью;
- `MultiJordan`: жадный выбор `k` центров, уменьшающих расстояния наблюдаемых зараженных до ближайшего центра.

Классические методы сначала сравниваются в режиме `oracle-k`. Они не должны получать информацию, недоступную GCN. Правила ничьих и случайные seed фиксируются.

**Результат этапа:** один evaluation pipeline принимает scores или предсказанное множество любого метода и формирует одинаковую таблицу метрик.

## 8. Node-only GCN

В `models.py` реализовать двухслойную GCN с узловой головой. Стартовые параметры: скрытая размерность 64, ReLU и dropout 0.2. Выход модели - один logit на узел.

В `losses.py` реализовать masked `BCEWithLogitsLoss`. `pos_weight` вычислять только по train-выборке внутри масок кандидатов. Модель обучается сначала без count-головы и consistency-loss.

Для вывода реализовать два режима:

- `oracle-k`: выбрать `k` кандидатов с наибольшими scores;
- `estimated-k`: применить порог, подобранный только на validation по macro-F1, и ограничить размер множества диапазоном 1-3.

Перед полноценным обучением модель должна переобучиться на 20 примерах. Если этого не происходит, продолжать массовые эксперименты нельзя.

**Результат этапа:** готовы Node-only GCN и Thresholded Node-only GCN, которые служат основными нейросетевыми baseline-методами.

## 9. Joint Source-Count GCN

Расширить общий GCN-backbone второй головой. Узловая голова остается прежней. Для count-головы объединить global mean/max pooling по всем узлам и pooling по наблюдаемым зараженным узлам, затем предсказать три класса количества источников.

В `losses.py` реализовать составную функцию:

```text
L = L_source + lambda_count * L_count + lambda_cons * L_cons
```

`L_count` является cross-entropy по классам 1-3. `L_cons` согласует сумму sigmoid-оценок кандидатов с ожидаемым количеством источников из count-головы. Значения коэффициентов подбираются только на validation по небольшой сетке.

В `inference.py` возвращать:

- узловые scores;
- распределение количества источников;
- предсказанное `k_hat`;
- итоговое множество top-`k_hat` источников.

Обучение ограничить 100 эпохами с early stopping по validation macro-F1 в режиме `estimated-k`, patience 10.

В `training.py` после каждой эпохи вычислять и сохранять отдельно для train и validation:

- общий loss и его части `L_source`, `L_count`, `L_cons`;
- macro-F1 и PR-AUC узловых scores;
- count accuracy и count MAE;
- learning rate и длительность эпохи.

Train-метрики считать без dropout в режиме `eval`, чтобы их можно было корректно сравнивать с validation. История сохраняется в CSV или JSON и строится в виде кривых `train/validation loss`, `macro-F1` и `count accuracy`. Лучший checkpoint выбирается только по validation macro-F1. Метрики test вычисляются один раз после выбора checkpoint и никогда не используются для early stopping или настройки гиперпараметров.

**Проверки:** модель способна переобучить маленький сбалансированный набор; count-голова выдает три logits; consistency-loss имеет конечное значение и передает градиенты; предсказанное множество всегда содержит 1-3 узла.

## 10. Обязательные абляции и эксперименты

В `run_experiments.py` реализовать запуск экспериментов по конфигурации и сохранение результатов в отдельную директорию. Каждый запуск должен сохранять конфигурацию, seed, checkpoint, историю обучения, итоговые метрики и предсказания.

Обязательная последовательность:

1. Сравнить все методы в `oracle-k` на Facebook.
2. Сравнить Thresholded Node-only GCN и Joint Source-Count GCN в `estimated-k`.
3. Обучить модель с двумя головами, но без consistency-loss.
4. Сравнить признаки `[infected]` и `[infected, degree]`.
5. Посчитать качество отдельно для `k=1`, `k=2`, `k=3`.
6. Проверить 100%, 75% и 50% наблюдаемых зараженных.
7. Проверить 0%, 5% и 10% ложноположительного шума.
8. Сравнить близкие и удаленные наборы источников.
9. Проверить модель, обученную на IC, на каскадах SI.
10. Проверить перенос Facebook -> email-Eu-core без дообучения.

Каждое обучение повторить минимум с тремя seed. Для метрик по каскадам считать 95% bootstrap confidence interval. Test-выборка не используется для выбора архитектуры, порога или коэффициентов функции потерь.

Для каждого запуска сохранять машинно-читаемый `metrics.json` со следующими группами:

- лучший epoch и причина остановки;
- train- и validation-метрики лучшего checkpoint;
- финальные test-метрики;
- метрики отдельно для `k=1`, `k=2`, `k=3`;
- confusion matrix для количества источников;
- время обучения, время inference, число параметров и максимальное потребление памяти, если оно доступно;
- версии Python, PyTorch, PyG, устройство и seed.

Для отчета автоматически формировать таблицы сравнения моделей и графики:

- train/validation loss по эпохам;
- train/validation macro-F1 по эпохам;
- count accuracy и count MAE по эпохам;
- качество по `k`, уровню наблюдаемости и шуму;
- среднее и 95% confidence interval по трем seed;
- разницу между train и validation как индикатор переобучения.

**Результат этапа:** таблицы и графики, позволяющие отдельно показать вклад count-головы, consistency-loss и структурного признака.

## 11. Отдельный режим со скрытыми источниками

После завершения основной постановки добавить модель, обучаемую с маской кандидатов `M=V`. В наблюдении допускается скрыть один истинный источник, поэтому loss рассчитывается по всем узлам графа.

Этот режим требует отдельного train/validation/test и не смешивается с результатами основной модели, где все источники присутствуют среди наблюдаемых зараженных. Его задача - показать возможность поиска за пределами видимой зараженной области, а не искусственно улучшить основную таблицу.

## 12. Визуализация и Streamlit

В `visualization.py` реализовать отображение графа, истинных источников, наблюдаемых зараженных, ложноположительных узлов и predicted scores. Для больших графов показывать локальную окрестность каскада или заранее рассчитанную раскладку, чтобы интерфейс не зависал.

В `app.py` сделать сценарий:

1. Выбрать граф и 1-3 источника.
2. Настроить `p`, число тактов и долю наблюдаемых узлов.
3. Запустить IC-симуляцию.
4. Показать истинный и наблюдаемый снимки.
5. Запустить модель.
6. Показать `k_hat`, итоговое множество, heatmap scores и метрики.

Для защиты подготовить сохраненные примеры, изображения и короткую анимацию на случай проблем с живым запуском.

## 13. Финальная проверка готовности

Разработка считается завершенной, когда:

- все unit-тесты симуляции, наблюдений, split и метрик проходят;
- integration- и smoke-тесты полного pipeline проходят одной командой;
- для критических модулей сформирован отчет о покрытии;
- датасет и обучение воспроизводятся по конфигурации и seed;
- готовы Uniform, Degree, Multi-Jordan, Node-only, Thresholded Node-only и Joint Source-Count GCN;
- выполнены обе ключевые абляции: без count-головы и без consistency-loss;
- получены результаты `oracle-k` и `estimated-k` отдельно для `k=1,2,3`;
- выполнены тесты неполноты, шума и переноса на email-Eu-core;
- сформированы таблицы с доверительными интервалами;
- сохранены train/validation-кривые и финальные test-метрики для каждого запуска;
- отчет содержит анализ сходимости, переобучения, времени обучения и inference;
- Streamlit запускает полный демонстрационный сценарий;
- сохранена таблица сравнения предлагаемого метода минимум с пятью ближайшими научными работами.

## Порядок реализации

Критический путь разработки:

```text
Инфраструктура
    -> графы
    -> IC-симулятор
    -> наблюдения
    -> датасет
    -> метрики и baseline-методы
    -> Node-only GCN
    -> Joint Source-Count GCN
    -> абляции и эксперименты
    -> Streamlit и материалы защиты
```

Временные признаки, GraphSAGE, реальные каскады и более трех источников реализуются только после полного прохождения этого критического пути.
